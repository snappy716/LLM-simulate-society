# 第 11 步：七天因果与玩家可感知性验收方案

状态：第 10 步收束后的执行方案，尚非本步骤通过证明。沿用现代校园、表里世界、20 名基础 LLM NPC 加额外好友；不提前编写第 13 步主线。

## 第一批先做可重复的对照底座

从一个经过真实行动形成、可以复现的校园事件起点，捕获完整世界与随机流检查点。各分支必须恢复同一检查点，而不是分别生成两个“看起来相同”的世界。记录代码版本、内容版本、种子、起始时钟及检查点摘要。

至少比较无玩家帮助与玩家尝试帮助两个七日分支。玩家侧只通过正式命令移动、交流、学习、接单或支持，保留失败与拒绝；不为使流程通过而清空 NPC 日程、恢复行动次数、提高关系或注入完成结果。测试前显式设置的边界条件须逐项披露，不能称为自然样本。

无帮助分支仅推进时段，不执行代办；只读采样不得标记已读、获得情报或改变后续决策。两个分支各完整推进 28 次，允许世界因真实竞争、资源、相遇和玩家行动产生差异，不要求结果相同或一定圆满。

## 采样必须回答的问题

| 问题 | 必须留下的证据 | 不接受的替代证明 |
| --- | --- | --- |
| 起因是什么 | 既有事件、现场、真实需求及其标识关联 | 任意写一段“发生了某事”的描述 |
| 谁决定做什么 | 当日计划来源、实际意图与约束、之后的改计划原因 | 只有模型回答或一张计划表 |
| 谁真的做了 | 正式命令结果、实际地点、行动与物资、接受/拒绝/过期 | 把接单、预约当成完成 |
| 改变了什么 | 同一人物/现场/任务/关系的前后状态与实际凭据 | 只报累计任务数或制造戏剧化旁白 |
| 玩家如何知道 | 当时可见的论坛、手机、现场、本人陈述、日志投影 | 用全知后台日志冒充玩家视角 |
| 后来是否延续 | 学习、回访、转交、竞争、失败后替代路径及未解决项 | 将每一天孤立展示或隐藏失败 |

后台审计可以保留游戏世界内部标识用于校验，但不能将未公开人物经历或其他人的私有计划送入玩家 UI。生成的报告须分开列“审计已知”和“玩家当时已知”。

## 再加入真实 LLM 分支

先让离线对照和 Godot 入口验证通过，再用相同检查点运行真实模型分支；规则与模型的主要差异应是合法候选中的选择、意图与受事实约束的表达，而不是赠送资源或额外行动。完整规划只在跨日执行。

记录实际模型、成功/失败/回退、请求与 Token、计划到执行的偏离以及自由对话实测。已有付费脚本可复用传输审计，但原脚本独立生成世界、只比较活动计数，不直接作为本步骤完整结论。真实连接需本轮验证，不把历史 API 成功写成当前成功。

付费验收使用有限天数与明确测试预算；游戏本身不新增聊天或好友觉醒的硬调用次数上限。无有效凭据时只标记真实模型分支待验，不假装接入成功，也不以离线假模型替代。

## 通过与后续修改顺序

1. 对照基础脚本、自身回归、完整 Python 与后台 Godot 测试通过后上传开发分支。
2. 检查自然链路缺什么，再补真实前置或玩家发现入口；每项仍全局复测后上传。
3. 真实模型七日与玩家/无人分支形成可追溯结论后，才收束第 11 步并进入第 12 步生活扩量。

“NPC 能自主行动”与“持续七天足够有趣”是不同结论。数量指标之外必须有人物动机、至少一条可核对的延续链和玩家可发现的变化；没有出现的类型应如实记缺口，不伪造自然涌现。
