# 校园社会模拟 RPG Demo 技术架构

> 状态：目标架构与渐进迁移基线
>
> 引擎：Godot 4.x，目标发行 Windows，macOS 用于开发测试
>
> 前置设计：`design/CAMPUS_WORLD_AND_GAMEPLAY_DESIGN.md`
>
> 迁移原则：保留 `project-a-0.2/`、`emergent_town_demo/` 和现有素材；新系统验证完成前不删除旧实现

## 1. 架构目标

本架构首先服务于自主社会，而不是把 LLM 直接接到每个角色上。

必须同时满足：

1. 约 200 名持久化 NPC 在无玩家、无 LLM 时也能连续运行 28 天。
2. 玩家与 NPC 使用同一时间、行动、物品、任务和战斗规则。
3. LLM 只能从规则生成的合法候选中选择，不能直接修改世界状态。
4. 表世界和里世界任务可被玩家或 NPC 原子锁定，不发生重复结算。
5. 玩家最多永久觉醒 6 名随机 NPC，同时总 LLM 深度槽位约 20。
6. 主线真相固定，参与者、过程、支线和失败后果允许动态变化。
7. Godot 负责显示、输入、地图、动画、音效和 UI；Python 负责权威模拟。
8. 使用现有人物分层动画、地图灰盒、Tile、物品和界面素材，不在本轮替换美术。
9. 开发机可以是 macOS，但仓库中不得写入 Mac 绝对路径，Windows 必须可运行。

## 2. 系统边界

```text
玩家输入
   ↓
Godot 表现层
   ↓ 版本化 JSON 请求
本地 Simulation API
   ↓
统一行动与事务边界
   ↓
权威世界状态 ──→ 事件日志 ──→ 快照/存档
   │
   ├─ 时间、人口、关系、经济、社团、论坛、任务
   ├─ 属性、检定、物品、成长、夜相、战斗
   ├─ NPC 规则决策与后台行动
   ├─ LLM 有限候选选择与表达
   └─ 主线锚点、局势和结局判断
```

### 2.1 Godot 是客户端

Godot 可以：

- 展示地图、角色、动画、交互范围和 UI；
- 采集玩家操作并发送结构化命令；
- 缓存只读快照，播放模拟事件的可视化结果；
- 在 Python 服务不可用时显示连接状态和重试。

Godot 不可以：

- 直接修改 NPC 金钱、物品、关系和任务状态；
- 自己判断任务是否完成或战斗是否命中；
- 保存与 Python 不一致的第二份权威世界；
- 在场景脚本中硬编码主线真相。

### 2.2 Python 是权威服务器

单机游戏也按本地服务架构处理。Python 负责：

- 权威时间、随机数种子和世界版本；
- 行动校验、检定、事务与事件产生；
- NPC 决策、日程、经济、关系、任务和战斗；
- LLM 上下文裁剪、响应校验和降级；
- 存档、迁移、重放和一致性检查。

## 4. 权威世界状态

未来 `WorldState` 应组合以下聚合，而不是继续向单个 `World` 类堆叠逻辑：

```text
WorldState
├─ clock                         天、时段、隐藏分钟、月相
├─ population                    200 名持久角色和背景人口统计
├─ places                        区域、开放状态、场景物品和通道
├─ inventories                   玩家、NPC、商店、容器库存
├─ relationships                 多维关系、承诺和见证关系
├─ organizations                 学院、社团和秘密组织
├─ forums                        表世界和里世界可见内容
├─ tasks                         任务状态、锁、协助者和结果
├─ situations                    正在发展的社会或异常局势
├─ battles                       当前战斗和后台行动
├─ knowledge                     书籍、案例、事实和认知边界
├─ narrative                     固定锚点、阶段 DDL 和结局条件
└─ cognition                     深度槽位、记忆摘要和待处理请求
```

每个聚合只能由对应系统修改。跨聚合操作通过统一事务协调，成功后一次性提交事件；任何一步失败都不能产生部分扣款、重复锁定或幽灵物品。

## 5. 统一命令、事件和事务

### 5.1 命令

所有玩家与 NPC 行为统一为命令：

```text
Command
├─ command_id                    幂等 ID
├─ actor_id
├─ action_id
├─ target_ids
├─ parameters
├─ expected_world_revision
├─ issued_day / phase / minute
└─ source                        player / rule / llm / narrative
```

处理顺序：

```text
解析契约
→ 检查世界版本与幂等键
→ 检查 actor、地点、时间和行动次数
→ 检查物品、技能、关系和知识
→ 执行检定
→ 在事务副本上应用结果
→ 验证金钱、库存、任务和战斗不变量
→ 原子提交
→ 写入事件日志
→ 投影 Godot 快照
```

### 5.2 事件

事件是已经发生的事实，不能把意图写成成功结果。公共字段：

- `event_id`、`event_type`、`day`、`phase`、`minute`；
- `actor_ids`、`target_ids`、`scene_id`；
- `command_id`、`causation_id`、`correlation_id`；
- `public_summary` 与系统 payload；
- 可见范围、严重度和知识标签。

事件同时驱动记忆、关系、论坛、任务、故事线和 Godot 表现，避免每个系统私下修改其他系统。

## 6. 时间与世界推进

玩家界面只显示上午、下午、晚上、凌晨；系统内部为每个时段分配隐藏分钟值，解决玩家与 NPC 论坛竞争和行动先后。

一个时段的权威推进顺序：

1. 接收本时段已登记的承诺与锁定任务。
2. 更新地点开放状态、日程和强制事件。
3. 生成玩家与 NPC 当前合法候选行动。
4. 规则 NPC 评分选择；深度 NPC 在预算内调用 LLM。
5. 按隐藏分钟、行动速度和冲突规则排序。
6. 逐个执行命令；每次执行后重新验证可能冲突的后续命令。
7. 处理目击、记忆、关系、伤势、需求和论坛反馈。
8. 生成只读快照并递增世界版本。

每天结束额外执行：疲劳与恢复、商店补货、任务过期、社团结算、关系反思、记忆压缩、次日日程与 LLM 槽位调度。

## 7. 人口与 NPC 模型

### 7.1 三层人口

- **背景人口**：约 5800，只产生人流、消费、舆论和公共需求。
- **持久化 NPC**：约 200，全部由规则逐人模拟。
- **深度认知 NPC**：同时约 20，在持久角色基础上增加 LLM 规划和自由表达。

角色不会因为退出 LLM 槽位而丢失状态。LLM 层是认知计算资源，不是世界实体。

### 7.2 角色组成

每名持久 NPC 由以下组件构成：

- 身份、学院/职业、住所与日程；
- 六项基础属性和派生战斗值；
- 专业熟练度、学院分支、社团和个人技能；
- 八维人格、核心价值、道德边界、恐惧和执念；
- 动态需求、情绪、伤势、污染和行动次数；
- 多维关系、承诺、秘密、记忆和身份锚点；
- 经济、库存、装备和最近成交记忆；
- 夜相感知、进入能力、意愿和当前队伍。

### 7.3 生成与晋升

NPC 使用 `content/npcs/generation_rules.json` 约束生成。背景人物因玩家相遇、任务或局势进入持久层时，必须分配稳定 ID 并永久保存。玩家觉醒要求该角色已持久化且满足关系、异常经历和身份锚点条件。

## 8. 决策与 LLM

### 8.1 规则评分

`simulation/systems/decision_scoring.py` 提供不依赖模型厂商的纯评分函数。候选行动综合目标、需求、价值、关系、承诺、人格、风险、金钱、时间、法律和道德成本。

规则 NPC 从高分合法行动中按确定性随机权重选择，不能永远机械选择第一名。评分结果保留贡献明细，供测试和 UI 解释“为什么这么做”。

### 8.2 深度认知

`FocusSlotAllocator` 先保留最多 6 个玩家永久觉醒角色，再根据活跃任务、夜间行动和世界相关性分配其余槽位。

LLM 输入只包含：

- NPC 当前可见和已知事实；
- 最近事件记忆与压缩长期记忆；
- 人格、价值、关系、需求和当前目标；
- 排名前 3～5 的合法候选及评分解释；
- 当前可用物品、行动次数和地点限制。

LLM 输出必须通过 `contracts/cognition_decision.schema.json`，只能选择候选行动或暂不行动。超时、非法输出或服务不可用时立即回退规则选择，不阻塞世界。

## 9. 双论坛与任务

论坛是世界状态的有限投影，不是全知任务菜单。

- 表世界允许 40～80 个并存任务，客户端筛选 15～25 个相关条目。
- 里世界维持约 20 个可见任务，其中每天约 6～10 个新任务。
- NPC 根据日程、手机习惯、关系、技能、风险和需求决定何时查看与接取。
- `TaskBoard` 使用 `lock_revision` 做乐观并发控制，确保玩家和 NPC 公平竞争。
- 已锁任务仍可被查看，也能申请协助、提供物资或观察结果。
- 失败和过期产生后果事件及后续任务，不静默删除。

任务模板只声明目标和验证条件；任务文本可以由规则模板或 LLM 表达，但完成判定只能读取权威状态。

## 10. 学院、社团和成长

八学院的四项公共能力和三条专业分支位于 `content/actions/college_skills.json`。十二个核心社团位于 `content/organizations/clubs.json`。

学院技能、专业分支、个人特质、社团技能、关系协作和失物印记全部引用稳定 `skill_id`，不把执行逻辑写入 JSON。内容文件提供参数，系统注册对应效果。

成长拆分为：

- 基础属性：增长慢，影响战斗与生活检定；
- 专业熟练度：决定是否会做以及检定加成；
- 知识理解：阅读 40%、案例 30%、应用 20%、反思 10%；
- 关系与身份锚点：解锁协作并抵抗遗忘；
- 社团身份：普通成员、骨干、负责人，拥有资源与组织权限。

## 11. 夜相与战斗

### 11.1 夜相状态

夜相不是第二个独立世界存档，而是地点在夜间条件下的另一组可见、通行、危险和交互状态。白天与夜相共用人物、库存、伤势、关系和事件。

进入夜相必须验证感知、入口、时段、状态、装备和意愿。玩家可以不进入；NPC 也可以拒绝邀请或独立组队。

### 11.2 战斗聚合

战斗使用独立 `BattleState`：

```text
BattleState
├─ battle_id / revision
├─ scene_id / situation_id
├─ participants / teams
├─ turn_queue / active_actor
├─ health / focus / pollution
├─ statuses / cooldowns
├─ known_weaknesses
├─ evidence_commands
├─ lost_heart_shell / coherence
└─ result / consequences
```

Godot 只发送 `combat_command` 并播放事件。玩家通常控制三人小队，但 NPC 的道德边界、极端恐惧、污染和关系反应仍可拒绝非法或违背角色底线的命令。

普通怪物使用规则战斗；失心者使用污染外壳、心结核心和异常自洽度。白天获得的证据、关系和身份锚点必须成为夜间可验证命令，而不是只提供文本提示。

玩家不在场时，以相同人物属性、技能、物品、知识、队伍协作和敌情做后台结算，并保留受伤、消耗、撤退、失踪和任务结果。

## 12. 主线架构

`demo_calendar.py` 和 `content/main_story/demo_calendar.json` 固定 28 天阶段边界。主线分三类数据：

1. **Truth**：教授已死亡、林默身份被覆盖等不可改写事实。
2. **Anchor**：阶段必须发生或必须判定的 DDL、证据和局势节点。
3. **Opportunity**：谁发现、谁保存、谁帮助、通过何种行动抵达锚点，可动态生成。

主线不会直接指定所有任务参与者。随机 NPC 可以发现、携带、泄露、毁坏或转交线索；系统只保证关键真相至少存在经过验证的替代获取路径。

## 13. API 版本规划

当前 `/snapshot`、`/step`、`/trade`、`/use_item` 和 `/action` 在迁移期间继续工作。新增功能使用版本化接口，成熟后合并到快照 v3。

建议端点：

| 端点 | 作用 |
| --- | --- |
| `GET /v2/world/view` | 玩家权限范围的世界投影 |
| `POST /v2/world/advance` | 推进当前时段 |
| `POST /v2/actions` | 统一玩家命令，支持幂等 ID |
| `GET /v2/forums/{kind}` | 获取经过权限和相关性筛选的论坛 |
| `POST /v2/tasks/{id}/claim` | 使用世界版本和锁版本原子接取 |
| `POST /v2/tasks/{id}/assist` | 申请协助或提供资源 |
| `POST /v2/cognition/awaken` | 请求记名，规则验证后执行 |
| `GET /v2/battles/{id}` | 战斗只读状态 |
| `POST /v2/battles/{id}/commands` | 提交战斗指令 |
| `POST /v2/saves` | 创建存档 |
| `POST /v2/saves/{id}/load` | 加载并迁移存档 |

所有改变状态的请求都要携带 `client_request_id` 和期望版本。重复请求返回第一次结果，不重复扣除资源。

## 14. Godot 迁移

### 14.1 保留内容

以下内容继续复用：

- `game/assets/characters/` 分层人物素材；
- `game/assets/maps/` 当前地图蓝图、道路与临时 Tile；
- 玩家移动、摄像机、NPC 外观生成和地图调试工具；
- 当前名册、物品与交易文字灰盒 UI；
- 现有本地服务启动与 HTTP 桥接方式。

地图中旧城镇名称和语义先通过内容映射适配为校园功能区，不为了改名重做图片。正式美术阶段再替换地图表现。

### 14.2 新 UI 顺序

1. NPC 详情增加六属性、人格摘要、学院、社团、关系和当前动机。
2. 增加表世界论坛和任务状态流。
3. 增加社团、课程、关系和队伍邀请。
4. 增加记名/觉醒选择与剩余槽位。
5. 增加里世界论坛、夜相切换和三人队伍。
6. 增加无站位战斗 UI。
7. 最后加入主线证据板、书籍理解和结局反馈。

## 15. 存档与兼容

当前快照保持 schema v2，现有测试继续锁定旧行为。校园字段完成运行时接入后再发布 schema v3，一次性增加：

- `clock.minute`、月相和阶段；
- NPC profile、学院、社团、人格、关系维度和模拟层级；
- 双论坛、任务锁和协助者；
- 觉醒槽位与认知摘要；
- 夜相状态、队伍、战斗和知识理解；
- 主线锚点与 DDL。

迁移必须采用“读取旧版、生成新对象、验证、原子写新文件”的方式，不原地破坏旧存档。每个存档记录内容版本和 RNG 状态，确保可重放。

## 16. 测试架构

### 16.1 单元测试

- 六属性范围和派生值公式；
- 人格决策权重和可解释贡献；
- 学院、社团、NPC 生成约束；
- 任务状态机、锁冲突、释放和过期；
- 觉醒槽位上限与动态分配；
- 战斗伤害、状态、污染和知识弱点；
- 主线阶段和 DDL。

### 16.2 契约测试

- 所有 JSON Schema 可解析；
- Python 输出符合契约；
- Godot 解析缺省字段不会崩溃；
- LLM 输出只允许候选行动；
- 请求幂等与旧版本冲突可预测。

### 16.3 集成测试

- NPC 需求产生任务，另一 NPC 查看、锁定、执行并结算；
- 玩家与 NPC 同时接取时只有一方成功；
- 商店和私人交易保持金钱、数量与物品实例守恒；
- 社团活动改变关系、资源和技能；
- 白天证据在夜间转化为战斗命令；
- LLM 超时后规则模式继续推进。

### 16.4 长跑测试

每个主要系统完成后运行至少 7～14 日；阶段系统完成后运行完整 28 日。检查：

- 无负数金钱、复制物品和重复任务奖励；
- 无 NPC 同时出现在互斥地点；
- 无行动次数、营业时间和 DDL 绕过；
- 普通私人交易平均间隔保持 2～4 天，职业角色允许更频繁；
- 论坛任务不会全部被同一类 NPC 垄断；
- 每晚进入人数与任务量处于目标范围；
- 主线关键真相不会被 LLM 修改或永久删除；
- 相同种子和输入产生可重放结果。

### 16.5 Godot 与发布测试

- macOS 使用 Godot 4.7 无界面导入与运行冒烟；
- Windows 使用 Python 命令和 Godot 导出后实际启动；
- Python 服务退出、端口占用和异常响应都有 UI 提示；
- 不提交 API Key、用户配置、`.godot/`、缓存和运行日志；
- 旧工程、旧 Python Demo、原 ZIP 和素材许可文件仍存在。

## 17. 四个月程序开发顺序

### 第 1 月：校园沙盒数据化

- 第 1 周：校园领域模型、内容契约、存档版本方案。
- 第 2 周：约束 NPC 生成、六属性、人格、关系和派生值。
- 第 3 周：统一行动和评分决策接入现有时间与物品系统。
- 第 4 周：表世界论坛、任务锁、发布/接取/完成闭环。

验收：规则模式下 200 NPC 连续运行 14 天，经济、物品、日程和任务无不变量错误。

### 第 2 月：校园生活与深度认知

- 第 5 周：八学院技能与三分支。
- 第 6 周：十二核心社团、活动、资源和晋升。
- 第 7 周：多维关系、承诺、协作与身份锚点。
- 第 8 周：LLM 候选选择、结构化记忆、20 槽位和 6 个觉醒名额。

验收：随机 NPC 能形成不同生活轨迹，觉醒前后行为连续，离线模式完整可玩。

### 第 3 月：夜相与战斗

- 第 9 周：污染、月相、夜相感知和里世界论坛。
- 第 10 周：三人队伍、邀请、准备和后台行动。
- 第 11 周：无站位技能回合制、物品、状态、弱点和失衡。
- 第 12 周：失心者、白天介入、夜间净化与多解法。

验收：玩家不参战时 NPC 也能发现、承接和处理夜相事件，结果反馈回表世界。

### 第 4 月：主线闭环与稳定

验收：可从第 1 天运行到第 28 天并进入至少一个结局；无 LLM 时主线和沙盒仍可完成。
