# 校园社团运行系统

> 状态：第 10 步可运行闭环已完成
>
> 范围：十二核心社团、成员身份、活动、出勤、贡献、资源、晋升、负责人、团队战术来源与手机 UI

## 1. 权威账本

`WorldState.organizations` 继续作为唯一社团权威状态。每个社团现在保存真实成员名单、逐成员档案、
唯一负责人、公共资源、活动次数与历史。逐成员档案包含普通成员/骨干/负责人身份、贡献、出勤、
缺勤、入社日期和晋升记录。Godot 只读取玩家可见投影，不自行计算职位或资源。

固定规则由 `content/organizations/clubs.json` 的 `runtime_policy` 提供；Python 负责验证和执行，UI
不硬编码结算数值。十二个社团继续使用各自独立的表世界实践技能与团队战术，不复制学院能力。

## 2. 入社和负责人

玩家与 NPC 可以加入多个社团，不设置统一会员数和“最多加入两个”的硬上限。入社需要满足至少一种
理由：学院交叉、完成社团任务形成声望、已有社团任务记录，或人物社交适配。已有社团越多，新增承诺
在自主决策中的吸引力越低。玩家必须在非深夜时段亲自到社团活动室申请。普通成员可以退出；负责人
必须先把职务原子交接给一名骨干，防止出现无负责人的中间状态。

开局负责人依据人物自律、外向、表达和稳定散列选择，而不是数组顺序。系统保留晋升空位：普通成员
达到贡献阈值、至少出勤三次且社团需要骨干时会晋升。十二个社团每天分别评估所有合适学生；每个
学生依据学院匹配、开放性、外向性、承诺压力、已有社团数量和当日意愿独立决定，因此一天可以零人、
一个人或多人入社，不设全校统一配额。

## 3. 活动、出勤、贡献和资源

每个社团在内容数据中拥有多个独立的每周活动时段，可分布在上午、下午和晚间；`CLUB_ACTIVITY` 仍
使用统一主要行动和地点规则。时间冲突和每时段主要行动次数会自然限制玩家与 NPC 实际参加的活动，
而不限制其社团身份数量。成功后，同一事务额外结算：

- 一次真实出勤，且同一时段不能重复计数；
- 基础贡献，并读取自律与学院交叉形成小幅加值；
- 社团公共资源增长；
- 满足条件时的晋升。

社团任务由成员完成时还会增加贡献和公共资源。每天上午统一结算上一天缺勤与公共资源维护成本。
所有变化与活动结果、任务结果一起提交；行动失败时不会出现“扣了次数但没记出勤”等半结算。

## 4. 团队战术边界

每个社团的 `night_skill` 现在成为稳定的团队战术来源，并有中文显示名、公共资源成本、两名同社团
成员的最低人数要求，以及至少一名骨干或负责人的组织要求。`USE_CLUB_TEAM_TACTIC` 已能验证参与者、
权限并原子扣除社团资源，产出正式事件。当前尚未实现战斗运行时，因此本阶段只完成战术解锁与资源
结算；具体卡牌效果在第 15～16 步接入 `BattleState`，不在社团模块伪造伤害结果。

## 5. 玩家可见表现

手机新增“社团中心”，显示十二社团的负责人、成员数、公共资源、玩家身份、贡献与出勤、入社评估、
表世界实践和团队战术。玩家可以在正确地点和时段申请入社、退出社团或消耗一次主要行动参加活动。

`CLUB_MEMBER_JOINED`、`CLUB_MEMBER_RECRUITED`、`CLUB_ACTIVITY_ATTENDED`、
`CLUB_MEMBER_PROMOTED`、`CLUB_LEADERSHIP_TRANSFERRED` 与 `CLUB_TEAM_TACTIC_PREPARED` 都进入统一
事件流，并由人物年表投影为组织经历。社团系统不另外维护一份面向 UI 的历史文本。

## 6. 下一步依赖

社团已经具备组队所需的身份、关系来源和团队战术来源。下一步实现完整关系与组队：邀请、拒绝、
承诺、队伍稳定度、关系协作能力和参战意愿。队伍运行时完成后，再把这里定义的团队战术装入战斗牌组。
