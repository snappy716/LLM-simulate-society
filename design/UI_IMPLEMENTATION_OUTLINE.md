# 校园 Demo UI 设计与实施大纲

更新日期：2026-09-11。

用途：作为后续 UI 设计、开发、联调和验收的参考基线。本文整理已讨论的整体 UI 范围，不是本轮新增功能的完成报告，也不直接开始 UI 改造。

## 1. 目标与使用方式

目前基础可玩系统已交付至实施路线第 12 步。UI 工作重点是把现有功能整理成完整、清楚、可操作的游戏体验，让玩家感受到：NPC 有自己的生活，任务会被其他人推进，自己的行为会改变人物和校园。

- 总体系统进度仍以 [IMPLEMENTATION_ROADMAP.md](IMPLEMENTATION_ROADMAP.md) 为准，不重编号、不撤销已有基础验收。
- 本文规定后续 UI 的范围、分批顺序和验收要求；既有实现记录见 [UI_FOUNDATION.md](UI_FOUNDATION.md) 与 [UI_RUNTIME_OPTIMIZATION.md](UI_RUNTIME_OPTIMIZATION.md)。历史截图和旧入口数量不代表当前最新布局。
- 开始每批工作前核对实际代码和接口，区分界面缺口与后端前置条件。已有面板优先整理复用，不另建重复系统。
- 新增展示需要新数据时，先补权威投影与测试；不能由 UI 或 LLM 编造状态。涉及未确定的玩法变化时停下询问。
- 本文中的“需要补充”是待实施范围，不表示已有；完成一批后记录日期、代码、验证和遗留问题，再勾选工作包。

状态说明：**已有待优化**表示已有操作入口但需整理体验；**需要补充**表示新增展示或交互，可能涉及接口；**后续预留**表示主线或正式发行阶段再完成。

### 当前优先批 用户指定的常驻 HUD

2026-09-11 补充：场景层由美术协作者完成，当前先做常驻信息层。以下位置与内容约束优先于本文 UI03 和此前通用布局建议；其他模块仍保留后续范围，不自动加入本批 HUD。

| 位置 | 本批允许内容 | 行为 |
| --- | --- | --- |
| 左上角 | 当前地点文字、日期、星期、时段 | 始终显示，紧凑布局 |
| 左上角下方 | 当前追踪事项、近期约定 | 默认只展开一件，可折叠 |
| 左下角 | 手机入口 | 始终显示；本时段首次收到新消息时短暂震动一次，此时段后续消息不再震动 |
| 右上角 | 地图、队友、人物状态与物品合并入口、卡牌库、关系 | 组成同一组，共五个入口；关系入口呈现交友和恋爱系统 |

- 上述区域不添加其他常驻内容；本批不额外挂生命/专注条、污染数值、行动计数、通知横幅、调试说明或结束时段按钮。人物状态与物品信息在合并入口打开后查看。
- 手机震动是图标的短暂视觉反馈，不是持续动画，也不是每条消息震动。按游戏日期与时段标识去重，不能因关闭手机或重建 HUD 重复触发；读取旧消息不算收到新消息。跨时段只允许新消息触发下一次，不因遗留未读自动震动。
- 合并入口内部保持人物状态与物品可分别访问，不因此合并后端数据模型。不得为隐藏旧 HUD 控件而删除原有功能；推进时间等操作应保留可达入口，具体入口迁移在实际实现前核对。
- 定稿图标：紧凑实心功能轮廓，冰白主体 `#dff5ff`、亮蓝点缀 `#1888ff`，不复制参考游戏资产。六枚分别为手机、折叠地图、双人、带人物负形的随身包、叠放卡牌、心形。去掉外侧星轨、底座、框线与复杂装饰；仅卡牌与关系保留月相切口，手机保持空屏。
- Godot 使用项目内 `game/assets/ui/campus_moon/` 的透明 SVG；按确认的概念方向重新绘制，不直接裁切概念图。当前采用可读性修正版：64 px 源画布、30 px 图形上限、46 px 热区；常态不透明亮白/清亮蓝，沿图形轮廓加细暗边，悬停/键盘焦点在 0.16 秒内渐亮，保留中文提示。日期和文字不再降低透明度，辅以细描边。保留紧凑布局，不增加面板、底框或发光装饰；不以融入场景为由牺牲可读性。
- 文字层级：地点 18 px，日期/星期/时段 13 px，以中点分隔；当前为亮白文字、细暗边，不再透明压暗。右上组同步收紧，保持同一基线和既定入口顺序。不会为追求融合而隐藏关键功能或缩小点击区至图形大小。
- 入口对应：地图→已有校园地图；队友→行动小队；人物与物品→人物状态/随身物品两个页签；卡牌库→角色八张牌组配置和本人可用牌的费用/效果；关系→交友恋爱协议与相处/约会。使用原权威数据与操作，不新增一套业务规则。
- 时间操作迁至手机顶部“时间与镜头”：保留结束时段、进出里世界和 1×/2×/3× 镜头操作。健康与行动信息移至内部状态页。原常驻调试文字、相机按钮与状态面板不再显示；调试场景保留原有测试节点。
- 追踪来自玩家已接的未完成委托与已确认约定；默认只展开一件，可切换、折叠和打开原详情。没有真实事项时不编造提示。日期沿用“第 N 天”，第一天星期一，与后端周循环一致；尚未指定的公历开学日期不虚构。

## 2. 共同原则

1. 延续写实校园风格。表世界与里世界可使用不同色调和细节，但保持同一套操作逻辑。现有七张场景图继续使用，临时图标和字体必须有清楚的许可来源。
2. 保留手机作为生活入口，复杂页面可展开为宽屏面板。正式战斗使用专用界面，不继续挤在手机表单里。
3. NPC 平常不显示调试状态文字。人物信息、位置、日志与动态均遵守玩家知情权限，不提供全校实时定位或全知内心。
4. 区分计划、承诺、实际执行和最终结果。聊天同意不等于正式预约，战斗胜利不必然等于任务完成。
5. 聊天、购物、吃饭、普通移动不扣主要行动；界面清楚展示真正消耗行动的操作，不新增分钟级时间管理。
6. Godot 展示权威数据并发送命令；模拟规则、伤害、费用、库存、任务锁和关系成立仍由后端校验结算。
7. 玩家即时 LLM 聊天不新增硬次数上限。开发测试控制付费调用，区分本地服务连接与模型 API 可用性，不泄露个人密钥。
8. 允许多位正式伴侣，各段关系独立确认与结束，不在 UI 中偷偷增加排他规则。
9. UI 验收不等于最终美术、长期故事质量或 Windows 发行验收。受控测试场景不能标成自然涌现结果。

## 3. 整体界面结构

| 层级 | 包含内容 | 职责 |
| --- | --- | --- |
| 场景层 | 校园、人物、物件、建筑与区域入口 | 自然呈现可见世界及交互目标 |
| 常驻信息层 | HUD、目标提示、少量通知 | 保留必要信息，不遮挡校园 |
| 手机与管理层 | 通讯、论坛、日程、人物、物品、生活 | 查询、规划和发起操作 |
| 专用玩法层 | 当面对话、调查现场、部署、正式战斗 | 为复杂玩法提供独立空间 |
| 系统层 | 开始游戏、存读档、设置、API、过场、异常提示 | 保证进入、恢复和继续游戏 |

## 4. 完整 UI 模块大纲

### UI01 公共视觉与交互规范

状态：公共主题与组件底座已实现，当前验收见 `production/UI01_UI02_ACCEPTANCE.md`；不代表其余业务页面完成专项视觉重排。

- 统一字体、字号、配色、图标、间距、面板和信息层级。
- 统一按钮、分页、搜索、筛选、滚动、弹窗和提示组件。
- 统一返回、关闭、确认、取消及键盘操作，区分主要、次要和危险操作。
- 覆盖加载中、无内容、不可操作、失败、结果尚未确认等状态。
- 对禁用操作解释原因；不能把未实现功能伪装成可用按钮。

### UI02 游戏开始与系统菜单

状态：标题、新游戏、继续、存读档、设置入口、引导与暂停菜单已实现，当前验收见 `production/UI01_UI02_ACCEPTANCE.md`。

- 标题页：继续游戏、新游戏、读取存档、设置、退出。
- 新游戏页面仅暴露当前已支持的角色与世界生成选项，不临时增加角色创建玩法。
- 初次进入的简短操作引导与暂停菜单。
- 存档列表展示日期、地点、已有时长信息和版本兼容情况；缺少的数据先补接口或不展示。
- 覆盖存档、返回标题和退出游戏的确认提示。

### UI04 地图与场景交互

状态：已有待优化，需要补充地点信息展示。

- 已知任务、约定、夜间区域和已发现异常的标记。

### UI05 手机首页与通知中心

- 重要通知与普通动态分级，避免持续弹窗。

### UI08 交友恋爱与深度交互

状态：已有待优化，需要补充关系总览。

- 发起相处、约会、关系确认、结束关系，以及接受、拒绝、取消、失约结果。
- 在基础 20 名 LLM NPC 之外，为符合条件的好友开启额外深度交互。
- 展示开启条件、当前状态及可能增加 API 用量的说明。
- 多位正式伴侣独立呈现，不替玩家自动同意，不凭高好感直接宣告关系成立。

### UI09 日程与行动安排

状态：已有待优化。

### UI10 双层论坛与任务管理

状态：已有待优化，需要强化动态反馈。

- 表世界与里世界论坛，帖子、委托、校园动态的分类筛选。
- 任务详情：来源、目标、地点、条件、奖励、截止时间。
- 真实的查看、考虑、接取、执行及结算状态。
- 我的委托、发布的求助和参与的协作。
- 被别人接走、完成、失败和到期后的记录。
- 任务追踪，以及人物、地点和线索跳转。
- 列表在实际变化时更新，不以假浏览量、假接单或通知制造繁荣。

### UI11 校园动态与事件回顾

状态：需要补充，优先级高。

- 今天发生的可知事件，以及 NPC 已完成的委托。
- 玩家关注的人物变化和短缺、纠纷、异常的发展。
- 玩家参与或未参与的事件结果及关联记录。
- 从事件追溯任务、人物和公开日志；只显示有证据的关联，不自动补因果。
- 可作为论坛内的“校园动态”分页，不强制增加独立应用。
- 全部摘要基于真实事件和知情范围，LLM 不为热闹编造结果。

### UI12 课程与校园生活

- 社团列表、成员、活动时间、贡献、晋升与公共资源使用确认。
- 比赛和节庆的报名、到场、个人表现和公开结果。
- 医院服务、治疗条件、费用与结果，以及休息恢复预览。
- 复用“列表—详情—报名—到场—结果”的活动组件，报名不等于完成。

### UI13 背包与交易

- 使用、赠送、丢弃、拾取、装备、卸下及必要的对象选择。
- 商品价格、库存、营业状态与购买结果。
- 私人报价、接受、拒绝和成交记录。

### UI14 调查与知识成长

- 现场可交互对象、搜索结果、询问、分享、保密和笔记。
- 已证实事实与人物推测的区别。

### UI15 队伍与卡组管理

状态：已有基础，需要重点补充。

- 可用卡牌浏览、来源、效果及当前规则支持的卡组配置。
- 战前资源、伤势和行动预算检查。
- 邀请成功、已经到场、可以上场分别显示；不把 UI 改造变成未经确认的新构筑规则。

### UI16 卡牌战斗专用界面

状态：规则已有，表现层需要重点重做。

1. 战前准备：任务目标、成员、前中后三排部署、确认开战。
2. 战斗主界面：双方角色卡、生命状态、敌人意图、手牌、共享费用和回合操作。
3. 操作反馈：选牌、合法目标、高亮、消耗与效果预览、伤害和状态变化。预览须由权威规则提供，不泄露隐藏信息。
4. 战斗结算：胜利、撤退、败北、消耗、伤势、知识成长和任务进度。

战斗胜利与现场任务完成分开呈现；胜利后仍需处置现场时，清楚提示下一步。表现可以先用简要素材，动作和定制美术由后续协作替换。

### UI17 跨日过场与次日简报

### UI18 设置与技术状态

## 6. 每批交付与验收

### 开始前

- 核对对应面板、后端投影、请求与事件，记录复用范围和缺失前置条件。
- 先明确页面入口、信息层级和主要操作，再实现组件；此大纲不规定所有按钮的最终尺寸。
- 保留用户的无关改动与私人文件，不因 UI 优化改动人物自主决策、行动计费或关系规则。

### 必测状态

- 正常操作、空列表、长文本、窄窗口和不同缩放。
- 等待、成功、业务拒绝、断线、结果未确认、无权限与资格失效。
- 返回、关闭、焦点、键盘可达性和输入草稿保留。
- 任务在查看中被接走、库存变化、邀约冲突等过期状态，提交时以服务端最新校验为准。
- 页面之间状态一致，UI 不产生额外资源、重复结算、免费行动扣时或隐藏信息泄漏。

### 完成条件

- 专项测试及与风险相称的全局 Python/Godot 回归通过，不能只凭控件存在勾选。
- 在 Godot 实际运行中检查布局和操作结果，关键页面保留带版本说明的截图。默认后台运行，不抢占前台；若当前环境不能完成视觉验证，应明确记录，不冒称通过。
- UI 变化不默认触发付费 API 多日重测；确需真实调用时使用有限样本，记录 Token 和验证范围。
- 记录完成内容、验证结果和剩余边界，才更新本节工作包状态。
- 后续实现批次沿用项目约定：测试通过后上传开发分支并核验，不合并 main。文档创建、代码实现、验证及上传分别记录，不将规划条目当成已完成功能。
- Windows 字体、输入、缩放和干净机器运行需实际验收，不能以 Mac 上通过替代。
